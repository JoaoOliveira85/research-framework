## Summary

Move per-cycle source access out of the scout stage and into a new
**source-extraction** pipeline stage. Cache signal payloads on disk keyed
by `(module, source_id, source_version)` so sources that haven't changed
serve from cache with zero LLM cost. The scout consumes cached signals
instead of re-walking sources every cycle.

Generalize the cache + extractor + validator + schema pattern into a
**pluggable source-module architecture**. Modules ship in the framework,
are selected per-vault in `settings.yaml::modules:` (install/update copy
only), get copied to `<vault>/modules/<name>/` at install time, and are
**discovered at runtime** by filesystem walk of `<vault>/modules/*/manifest.yaml`.
Source instances to extract come from each module's
`<vault>/modules/<name>/sources.yaml` (not `research.spec.md::data_sources`;
that list remains scout/schema-gen context only per FR-013c). Trigger
patterns route generic-path fallbacks and debugging; enumerated instances
use `source_id` derived per FR-013b. The code module is the first
(and only ship-now) module; YouTube, Reddit, O'Reilly, and any future
source-specific modules drop in later without spec changes.

Target release: **0.3.0**. This is the first 0.3.x architectural change \u2014
the 0.2.x line stays patch-only after 0.2.31.

Headline wins (measured against the user's reference-vault-0.2.30 baseline):

- 60%+ reduction in source-walk-path token spend
- 2\u00d7+ new-topic yield per cycle (scout's freed attention can pursue
  spec coverage gaps instead of re-extracting known facts)
- Domain-agnosticism made structural (Constitution 1.3.2): per-vault
  per-module schemas mean the same framework drives Java-Spring
  vaults, ESP32 firmware vaults, and ML research vaults without code
  changes.

## Technical Context

**Language/Version**: Python 3.11+ (per constitution Technology Constraints).

**Primary Dependencies**: Existing only \u2014 `jinja2 \u2265 3.1`, `pyyaml \u2265 6.0`,
`sqlite3` (stdlib). **No new runtime dependencies** \u2014 Principle V is
non-negotiable. The bridge is invoked as a subprocess like every other
pipeline stage; it reuses the existing `scripts/agent_call.py` dispatch
path for any LLM work it does (schema-gen calls, extractor invocations,
consensus calls). Module-discovery walks the filesystem; trigger matching
uses stdlib `re`.

**Storage**: Filesystem under vault root. New artifacts:

**Testing**: pytest. Tier-1 unit tests for cache, validators, schema
parsing. Tier-2 contract tests for the signal-payload envelope, watermark
protocol, manifest schema, and trigger registry. Tier-4 e2e test that runs
a full cycle with a fake module + fake source and verifies cache-hit
behaviour on the second cycle. New helpers in `tests/_helpers/fake_repo.py`
(disposable git checkouts with controlled SHAs) and
`tests/_helpers/fake_module.py` (stub modules with controllable
extractor behaviour for testing the module-architecture surface).

**Target Platform**: macOS + Linux. The bridge MUST work under codex's
`workspace-write` sandbox \u2014 i.e. all bridge artifacts MUST land under
`<vault>/_pipeline/` or `<vault>/modules/`. The bridge MAY read anywhere
the parent process can read (specifically, anywhere modules need to read
to fulfill extractions); it MUST NOT write outside the vault.

**Project Type**: CLI library extension \u2014 single Python project,
`src/research_framework/pipeline/source_bridge/` package +
`src/research_framework/modules/` module tree + `scripts/source_bridge.py`
entry point + `tests/source_bridge/` test tree + `tests/modules/code/`
for the first reference module.

**Performance Goals**:

- **SC-001 (spec)**: unchanged-vault second cycle stage completes in
  under 500 ms total. Means the cache-hit fast path does no I/O
  beyond reading `watermarks.json` and the relevant signal files.
- **SC-002 (spec)**: \u226560% reduction in source-walk-path tokens vs
  0.2.30 baseline on the user's reference-vault spec.
- **SC-003 (spec)**: \u22652\u00d7 new-topic yield per cycle.
- **SC-006 (spec)**: schema-gen produces visibly different schemas
  for structurally-different vault specs (load-bearing test for
  Constitution 1.3.2).
- Full test sweep stays under 8 min (current 0.2.31: ~5:14; budget
  room for ~30 new integration tests across source-bridge + modules).

**Constraints**:

- No new runtime dependencies (Principle V).
- Backwards-compat with 0.2.31 vaults: vaults generated under 0.2.31
  must remain operable. The bridge is opt-in via
  `settings.yaml::stages.source_extraction.enabled` defaulting to
  `false` until 0.3.0 ships; on 0.3.0 default flips to `true` and the
  migrator (013) writes the flag during `./vault update`.
- Domain-agnosticism (Constitution 1.3.2): no hardcoded bucket
  enumerations in source. Schema is generated. Tests MUST include at
  least one non-web-microservices fixture (e.g. embedded firmware).
- Sandbox-write compatibility: bridge writes only under
  `<vault>/_pipeline/` or `<vault>/modules/`.
- Module trust boundary: modules execute arbitrary Python in-process.
  Documented in the module-authoring quickstart + install wizard
  prompt.

**Scale/Scope**:

- Target: 5\u201350 sources per vault across all modules.
- Each signal payload: ~5\u201320 KB typical, 100 KB hard cap with
  truncation flag.
- Cache grows linearly with `sources \u00d7 distinct_versions_observed`.
  GC keeps this bounded (30-day default; settable).
- Estimated test counts at ship: ~1240 (current 0.2.31: 1187 + ~50
  new for source-bridge + modules + schema-gen + agent-call logging).

## Locked Decisions (was: `[NEEDS DECISION]`)

Each entry resolved as of 2026-05-20. These flip the original draft's
four open questions into firm commitments. The Phase 0/1/2 sections
below assume these are settled.

### [DECIDED 2026-05-20] D1 \u2014 Facts schema is dynamically generated, not enumerated

**Resolution**: Schema-gen stage produces a per-`(vault, module)` JSON
Schema at install time + on spec-hash change. The 9 buckets we discussed
during brainstorming (`technologies`, `patterns`, `data_stores`,
`api_protocols`, `external_services`, `documentation`, `adrs`,
`decisions`, `business_logic`) become FEW-SHOT EXAMPLES in the schema-gen
prompt at `contracts/facts-schema-gen-prompt.md`, NOT hardcoded defaults
in framework code. Fallback on schema-gen failure: 3-bucket minimal
default (`technologies`, `patterns`, `notable`) for that pair, logged
loudly.

**Rationale**: Constitution 1.3.2 ("domain-agnostic by construction")
forbids hardcoded domain-specific enumerations. Schema-gen makes the
schema a DATA artifact derived from the spec at runtime, not a CODE
artifact. Cost: one Haiku call per `(vault, module)` at install. Tens of
cents per vault lifetime, effectively free.

**Implementation**: Block S (Schema-Gen) handles this. See Phase 2.

### [DECIDED 2026-05-20] D2 \u2014 Value-tiered consensus, caller-decides

**Resolution**: Bridge invocations accept a `value_tier` parameter
(`routine | important | critical`). Settings maps tier \u2192 odd N
(defaults: routine=1, important=3, critical=5). Framework validates N is
odd at config-load time; rejects even values with a clear error. v1
ships with all invocations defaulting to `routine` (N=1) until
escalation heuristics emerge. For N\u22653: majority vote on verdict, UNION
of findings (additive). Per-repo override possible via
`settings.yaml::stages.source_extraction.invocations.<source>.value_tier`.

**Rationale**: Replaces the original spec's "always N=2 with union on
disagreement" model. Odd N avoids ties by construction. Tier-based
escalation lets the caller spend tokens only when the verdict matters,
not on every routine extraction. ConsensusResult audit record captures
all extractor verdicts + the final majority result for reproducibility.

**Implementation**: Block C (Extractor + Consensus) handles this. See
Phase 2.

### [DECIDED 2026-05-20] D3 \u2014 Time-based 30-day signal GC

**Resolution**: Signals retained for 30 days. The watermark IS the
pointer to "current" \u2014 GC of older files NEVER affects the cache-hit
path. Audit trail (`consensus/`, `bridge.log`,
`cycles/cycle-NNN/agent-calls/`) is **never** auto-GC'd \u2014 those are
the post-mortem surface. Setting:
`stages.source_extraction.signal_retention_days: 30 | 0` (0 = never
GC).

**Rationale**: Disk math (~3 MB/month/vault) makes count-based GC
over-engineering. Time-based is simpler, more predictable, and matches
how the user thinks about retention.

**Implementation**: Block A (Cache + Schema) handles GC in the cache
writer. See Phase 2.

### [DECIDED 2026-05-20] D4 \u2014 Extractor prompt content deferred to implementation; per-call agent logging added

**Resolution (part 1)**: Prompt content for each module's extractor is
NOT a design-time decision. The framework ships a v1 prompt per module
(`contracts/extractor-prompt-<module>.md`), tunes against the user's
test vaults until SC-002 / SC-003 metrics hit, and locks as v1. Vault
authors don't override the prompt at v1 (would require forking the
module); a per-vault prompt-override mechanism is a v2 concern.

**Resolution (part 2)**: Add a cross-cutting FR (FR-024 in spec) for
per-call agent logging. Every agent invocation across the framework
(scout, note-writer, verifier, schema-gen, source-extraction, ALL of
them) writes a record to
`_pipeline/cycles/cycle-NNN/agent-calls/<ts>-<stage>-<call-id>.json`
with full prompt + response + cost + latency captured. Capture happens
at `agent_call.py` so no stage opts in or out. Lands as its own commit
during the 0.3.0 work, NOT as a separate spec.

**Rationale**: Prompt content is iterative quality-tuning, not
architectural. The agent-call logging is the missing observability
surface that makes that tuning possible \u2014 you can't tune what you
can't audit.

**Implementation**: Block C (Extractor) handles part 1. Block O
(Observability) handles part 2. See Phase 2.

### [DECIDED 2026-05-20] D5 \u2014 Module trust boundary: permissive + documented

**Resolution**: v1 trusts modules and per-vault validators in-process.
No technical sandbox in 0.3.0. The install wizard surfaces a warning
when `settings.yaml::modules:` is non-empty; `quickstart-module-author.md`
opens with a bold trust-boundary warning. A future sandbox (subprocess
isolation + restricted env) is acknowledged as follow-up work outside
020's scope; the v1 contract is shaped so a sandbox can land later
without breaking module authors.

**Rationale**: Matches the existing `<module>.validators.py` trust
model already accepted in 020. Building a sandbox at v1 would
dramatically expand scope and delay 0.3.0. Documentation is the
appropriate v1 enforcement mechanism for a single-user / known-author
deployment model.

**Implementation**: Block I (Integration) wires the install-wizard
warning. Block D (Docs) writes the trust-boundary section in
`quickstart-module-author.md`.

### [DECIDED 2026-05-20] D6 \u2014 Module version compatibility: auto-rebuild scoped to installed

**Resolution**: On `./vault update`, the migrator (013) re-copies
each module **listed in `settings.yaml::modules:`** from the new
framework bundle. Modules NOT in the list are NOT auto-copied even if
the bundle has them \u2014 the user's explicit module-selection is
respected at every update. Framework code under the module dir refreshes;
**`sources.yaml` and `manifest.user_owned` paths are preserved if present**
(FR-025; bundle template seeded only when absent). Cache invalidates per
existing FR-006 on `bridge_version` mismatch.

**Rationale**: Modules are infrastructure for framework code; operator-
owned enumeration (`sources.yaml`) must survive updates.
Auto-rebuild matches the "drop in and the framework just works" UX.
Scoping to the installed list preserves user intent across updates \u2014
no module is silently added.

**Implementation**: Block CFG (Settings + Migrator) extends the
migrator hook. New task: "Migrator copies named modules on update."

### [DECIDED 2026-05-20] D7 \u2014 Schema-gen model via vendor-agnostic tier table

**Resolution**: Introduce a top-level `tiers:` block in
`settings.yaml` mapping declarative complexity names (`basic`,
`normal`, `flagship`) to vendor model identifiers (e.g.
`basic: claude-haiku-4.6`, `normal: claude-sonnet-4.6`,
`flagship: claude-opus-4.7` for Claude users; codex equivalents for
codex users). New stages introduced in 020 (`schema_gen`,
`source_extraction`) reference tiers via a `tier:` field on the
executor; the framework resolves `tier: basic` to the model identifier
at config-load. Schema-gen defaults to `tier: basic`. Module manifests
MAY declare a `default_tier:` so module authors signal expected
complexity. Stages with both `tier:` and `model:` set MUST error at
config-load (mutually exclusive). Existing stages (`scout`,
`note_writer`, etc.) keep their current `model:` field; migration to
tiers is OUT OF SCOPE for 020.

**Rationale**: Vendor-agnostic complexity tiers let vault authors swap
model providers in one place. Module authors can signal complexity
without knowing the user's runtime. Scope-bounded to NEW stages so
020 doesn't grow tentacles into settings-template migration.

**Implementation**: Block CFG (Settings) ships the `tiers:` block.
Block S (Schema-Gen) consumes `tier: basic`. New task: "Config-load
validation: error on `tier`+`model` conflict, error on missing tier."

### [DECIDED 2026-05-20] D8 \u2014 Schema drift on manually-edited schemas: fail-closed unless forced

**Resolution**: When `manually_edited: true` AND
`<vault>/_pipeline/sources/<module>/.schema-gen-hash` doesn't match the
current `research.spec.md` hash, the framework MUST:
1. Run schema-gen anyway to sidecar
   `_pipeline/sources/<module>/facts-schema.regenerated.json`.
2. Write a structural diff to
   `_pipeline/sources/<module>/facts-schema.drift.md`.
3. **Fail the next cycle** with a clear error citing the drift file and
   three resolution paths.

The user resolves by: (a) merging the sidecar into the manual schema
and acknowledging via a CLI flag that bumps the watermark, (b) removing
`manually_edited: true` to re-enable auto-regeneration, or (c) passing
`--force-stale-schema` to proceed knowingly with the stale schema.

**Rationale**: User opts into responsibility when setting
`manually_edited: true`. Framework refuses to silently honour a stale
contract. Matches the existing fail-closed posture on validation
errors.

**Implementation**: Block S (Schema-Gen) implements drift detection +
sidecar + diff. Block I (Integration) wires the `--force-stale-schema`
flag on the cycle-running CLI.

### [DECIDED 2026-05-20] D9 \u2014 Module-isolation policy with retry-once

**Resolution**: When any module-subsystem call (extractor invocation,
validator YAML evaluation, validator Python execution, manifest
parsing during discovery) raises an unhandled exception:
1. **Retry the call ONCE** with the same input.
2. If retry also fails: log error + traceback to `bridge.log` AND via
   the per-call agent-log surface (FR-024).
3. **Salvage any partial output** the module produced before the
   exception \u2014 write to cache with `verdict: "error"` and
   `partial: true`.
4. Mark the source as failed for this cycle (signal = partial payload
   OR empty if nothing produced).
5. Continue the cycle with other sources.
6. **Surface failure in the cycle's run-report** so the vault author
   sees it without digging through logs.

Cycle ALWAYS continues on per-source failure. No flag overrides this
behavior (separate from D8's `--force-stale-schema`, which is for
schema drift, not module exceptions).

**Rationale**: The modular architecture exists specifically to isolate
complex, failure-prone flows from the main research loop. A failing
module MUST NOT bring down the cycle. Retry-once handles transient
issues (e.g. flaky network); salvage preserves useful work; run-report
surfacing closes the visibility gap.

**Implementation**: Block C (Extractor + Consensus) implements
retry-once for extractor invocations. Block V (Validators) implements
retry-once for validator exceptions. Block M (Module discovery) handles
manifest parse failures. Block I (Integration) wires run-report surfacing.

## Phase 0 \u2014 Research (to be written into `research.md`)

Implementation-time decisions that need to land BEFORE writing
contracts. Each item has a proposed answer; can be overridden during
plan review or research.md write-up.

1. **Git invocation strategy for the code module.** Use
   `subprocess.run(['git', 'rev-parse', 'HEAD'])` for SHA reads and
   `subprocess.run(['git', 'log', '--name-only', '--since=...'])` for
   the freshness window. Pure stdlib; same pattern as
   `src/research_framework/pipeline/migrator_git.py`.
2. **Subprocess invocation pattern for the bridge.** Bridge spawns
   from `cycle_runner` via
   `subprocess.run([sys.executable, 'scripts/source_bridge.py', ...])`,
   same shape as `agent_call.py`. Returns rc=0 on cache-hit, rc=0 on
   successful extraction, rc=2 on hard failure; bridge log to stderr.
3. **Module subprocess invocation pattern.** Bridge spawns each module's
   extractor via
   `subprocess.run([sys.executable, '<vault>/modules/<name>/extractor.py', ...])`
   with structured stdin (JSON: source_id, version, schema, value_tier)
   and structured stdout (JSON SignalPayload). Module manifest's
   `entry_point` field names the file. Status-file heartbeat at
   `_pipeline/sources/<module>/.status/<source-id>.json` for liveness.
4. **Signal-payload size limits.** Hard cap 100 KB per payload. If
   the extractor produces more, truncate with `truncated: true` flag
   in the envelope. Tested via tier-2 contract.
5. **Schema versioning.** `bridge_version` field in every payload AND
   in `watermarks.json`. On mismatch \u2192 invalidate cache, re-extract.
6. **Spec-hash for schema-gen invalidation.** Store
   `<vault>/_pipeline/sources/<module>/.schema-gen-hash` containing
   sha256 of `research.spec.md`. On mismatch \u2192 regenerate schema.
   UNLESS `facts-schema.json` has `manually_edited: true` set (then
   never regenerate).
7. **Concurrent extractor invocations for consensus.** Use
   `concurrent.futures.ThreadPoolExecutor(max_workers=N)` for
   consensus; bounded N matches the resolved value_tier. No
   async/await \u2014 keeps the subprocess flow simple.
8. **First-match-wins trigger ordering.** Use
   `settings.yaml::modules:` array order as registration order;
   first matching trigger wins. Document via `--debug-triggers`
   flag on `scripts/source_bridge.py` that prints the registry +
   match attempts for a given source.
9. **Manifest-discovery cadence.** Walk
   `<vault>/modules/*/manifest.yaml` on every pipeline start (cost:
   <10 ms for typical 5-module vaults). Don't cache the registry
   between runs \u2014 simplifies the "drop in a module folder" UX.
10. **Module trust boundary.** Documented in TWO places: (a) the
    install wizard prompts "Modules execute arbitrary Python; only
    install modules you trust. Continue?" when `modules:` is
    non-empty; (b) `quickstart-module-author.md` opens with a
    bold warning. NOT enforced technically in v1 \u2014 manual
    discipline only.

### Data model

- **SignalPayload** (envelope shared across modules, content per-module):
  ```json
  {
    "module": "code",
    "source_id": "/abs/path/to/repo",
    "source_version": "abc123def456",
    "bridge_version": "0.3.0",
    "extracted_at": "2026-05-20T10:00:00Z",
    "verdict": "ok | empty | exhausted | error",
    "facts": { /* shape per per-(vault, module) schema */ },
    "notable": [
      {"observation": "...", "confidence": "high|medium|low", "evidence_ref": "src/...:42"}
    ],
    "truncated": false
  }
  ```
- **Watermark** (per-source entry):
  ```json
  {
    "/abs/path/to/repo": {
      "source_version": "abc123",
      "bridge_version": "0.3.0",
      "extracted_at": "...",
      "verdict": "ok | exhausted",
      "consensus": {"n": 3, "majority": 2, "agreed_at": "..."}
    }
  }
  ```
- **ModuleManifest** (`<vault>/modules/<name>/manifest.yaml`):
  ```yaml
  name: code
  version: 1.0.0
  description: Extracts structured + freeform signals from git repositories.
  triggers:
    - type: path_pattern
      pattern: '.+\.git$|.+/\.git$'
    - type: path_exists
      pattern: '.+/.git/HEAD'
  entry_point: extractor.py
  default_value_tier: routine
  schema_examples: few-shot.md
  ```
- **TriggerRegistry** (in-memory): ordered list of
  `(module_name, trigger_type, compiled_pattern)` tuples. Built at
  pipeline start from manifest scan.
- **ConsensusResult** (per-source per-cycle audit):
  ```json
  {
    "module": "code",
    "source_id": "...",
    "cycle": 3,
    "value_tier": "important",
    "extractors_spawned": 3,
    "verdicts": ["ok", "ok", "exhausted"],
    "final_verdict": "ok",
    "findings_unioned": 14,
    "dissenting_extractor_indices": [2]
  }
  ```
- **AgentCallRecord** (per-LLM-call audit, FR-024):
  ```json
  {
    "stage": "schema_gen",
    "call_id": "abc-def",
    "timestamp": "2026-05-20T10:00:00Z",
    "model": "claude-haiku-4",
    "prompt": "...",
    "response": "...",
    "latency_ms": 412,
    "tokens_in": 1234,
    "tokens_out": 567,
    "cost_usd": 0.0023,
    "error": null
  }
  ```

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Module subprocess deadlocks on a hung agent CLI. | Default 600 s timeout per extractor; consensus marks the dissenting timeout as "no verdict" and falls back to N\u22121 majority. |
| Cache file corruption (interrupted write). | Atomic write via `tempfile.NamedTemporaryFile` + `os.replace`. Already the pattern in `validate_cycle.py` sidecar writer. |
| Vault-author Python validator does file I/O or makes network calls. | `validators.py` runs the user's `validate(payload)` in the SAME process \u2014 we trust it. Documented in `quickstart-vault-author.md`. |
| Module-author Python extractor does malicious things. | Trust boundary documented in install wizard + `quickstart-module-author.md`; no technical enforcement in v1. Future v2 could sandbox via subprocess + restricted env. |
| `bridge_version` mismatch on every update wastes a full re-extract. | Most updates won't bump `bridge_version`. Reserve bumps for actual schema changes. Migrator (013) handles the bump per release. |
| Schema-gen produces wildly inconsistent schemas across vaults. | The few-shot examples in `facts-schema-gen-prompt.md` anchor the agent. Loud WARN + fallback ensures bad output never silently degrades the cycle. Test fixtures verify the two-fixture diversity expectation (SC-006). |
| Two modules with overlapping triggers produce non-deterministic routing. | First-match-wins is deterministic (`settings.yaml::modules:` order). `--debug-triggers` exposes the registry. Documented in `quickstart-vault-author.md`. |
| Vault author manually edits `facts-schema.json` and confuses themselves later. | Required `manually_edited: true` field is the explicit opt-out signal. Framework respects it. Documented. |
| Per-call agent logging balloons disk usage. | Per-call records are ~5\u201320 KB typical; even 1000 calls/cycle is ~20 MB. Cycle-scoped storage means old cycles can be archived. If it becomes a problem, add per-call compression as a follow-up. |

## Cross-spec coordination (Spec 020 ↔ Spec 023)

Both specs ship in the revival sprint and share one **filesystem-level**
integration point that `/speckit.tasks` should respect:

- **`<vault>/scripts/` lifecycle is owned by spec 023 FR-015.** Spec
  023 Phase 1 guarantees that vault-local `scripts/collect_*.py`
  files (plus the `reddit_rss.py` frozen-allowlist entry) survive
  `./vault update`. Spec 020's module ports remove these collectors
  one at a time — but the *removal* step (delete the
  `scripts/collect_*.py` once its module port lands) is gated on
  spec 023's `scripts/`-survives-update guarantee being in place
  first, so that operators don't lose mid-port code to a stray
  update wipe.

- **No code coupling at the `refresh-sources` boundary.** Spec 023's
  `refresh-sources` CLI iterates `<vault>/scripts/collect_*.py` (+
  allowlist) only. It does NOT read `<vault>/modules/*/sources.yaml`.
  Conversely, spec 020's `source_bridge/sources_loader.py` reads
  per-module `sources.yaml` only and does NOT shell out to legacy
  collectors. The two systems coexist filesystem-side, in different
  directories, with no cross-invocation. ADR-0009 option A is the
  migration policy that draws the line here.

- **Implication for `/speckit.tasks` generation**: 020's tasks should
  NOT add any direct dependency on `cli/refresh_sources.py` (spec 023's
  new module). If `/speckit.tasks` proposes a task that would have
  `sources_loader.py` invoke or be invoked by `refresh-sources`,
  that's a signal to revisit the boundary — the explicit decoupling
  is intentional. The only shared concern is the `scripts/`
  filesystem lifecycle described above.
