# Quickstart: Source Modules for Vault Authors

You're using a research vault generated by `research-framework`.
0.3.0 adds **source modules** — pluggable adapters that pull
structured signals from data sources (code repos, YouTube videos,
Reddit threads, etc.) so the research pipeline can spend its tokens
on intent-first thinking instead of re-reading the same source on
every cycle.

This quickstart shows you how to:

1. Enable source modules in your vault.
2. Declare **what to extract** in per-module `sources.yaml` files.
3. Keep `data_sources` in `research.spec.md` for scout coverage (separate role).
4. Run a cycle and inspect the cached signals.
5. Tune the per-vault facts schema and handle drift.

> **Scope:** This guide is for vault authors. If you're building a
> NEW module (e.g. a Twitter module), see
> [`quickstart-module-author.md`](./quickstart-module-author.md).

## 1. Enable source modules

In `<vault>/settings.yaml`, add the `modules:` block (or check it's
already populated from the install wizard):

```yaml
modules:
  - code
  # - youtube   # uncomment to copy youtube from bundle on install/update
```

`modules:` controls **which modules get copied** from the framework
bundle on `install.sh` / `./vault update`, and the **order** used when
two modules' triggers could match the same URL. It does **not** gate
runtime discovery: any folder under `<vault>/modules/<name>/` with a
valid `manifest.yaml` is active on the next pipeline start (SC-007).

Enable the source-extraction stage:

```yaml
stages:
  source_extraction:
    enabled: true
    tier: basic
```

Confirm your `tiers:` block defines `basic`:

```yaml
tiers:
  basic: claude-haiku-4.6
  normal: claude-sonnet-4.6
  flagship: claude-opus-4.7
```

## 2. Declare sources in per-module `sources.yaml`

**This is the primary operator surface for extraction.** For each module
you use, edit (or create) `<vault>/modules/<name>/sources.yaml`.

Example — code module:

```yaml
# <vault>/modules/code/sources.yaml
github_repos:
  - path: /Users/me/src/my-microservice
    value_tier: important
  - path: /Users/me/src/my-monolith
    value_tier: routine
```

Example — youtube module (when installed):

```yaml
# <vault>/modules/youtube/sources.yaml
youtube_channels:
  - url: https://www.youtube.com/@SomeChannel
    label: Some Channel
```

The framework reads this file on every cycle, derives a stable
`source_id` per record (using `manifest.yaml::source_id_from`), and
runs that module's extractor when the source version changes.

If `sources.yaml` is missing for a discovered module, that module
contributes **zero** extractions (WARN once per pipeline start).

After `./vault update`, your edited `sources.yaml` files are **never
overwritten** if they already exist (FR-025). Framework code under the
module folder may still refresh.

### `research.spec.md::data_sources` (scout / schema-gen only)

Keep (or add) sources in `research.spec.md` for **coverage framing** and
schema generation. The extraction loop does **not** iterate this list
alone in 0.3.0.

During migration you may duplicate the same repos/channels in both
places; keep them in sync manually until a future spec adds
cross-validation.

```yaml
# research.spec.md — still useful for scout + schema-gen
data_sources:
  - kind: code
    url: /Users/me/src/my-microservice
  - kind: youtube
    url: https://www.youtube.com/@SomeChannel
```

### Debug trigger routing

Triggers on `manifest.yaml` are for **generic-path routing** and
debugging, not for discovering instances already listed in
`sources.yaml`:

```bash
python scripts/source_bridge.py --debug-triggers /Users/me/src/my-monolith
```

## 3. Run a cycle and inspect signals

```bash
./generate_vault.sh
```

After the cycle:

```
<vault>/_pipeline/sources/
└── code/
    ├── facts-schema.json
    ├── watermarks.json
    ├── signals/
    │   ├── my-microservice-abc123.json
    │   └── my-monolith-def456.json
    └── consensus/
```

Each `signals/*.json` is what scout consumed. Open one to verify
`source_id` matches your `sources.yaml` paths/URLs.

## 4. Tune the per-vault facts schema

Same as before: `facts-schema.json` under `_pipeline/sources/<module>/`
is generated from `research.spec.md` + `data_sources` + module few-shot.

```bash
cat <vault>/_pipeline/sources/code/facts-schema.json
research-framework schema --regenerate code
```

Manual edit: set `"manually_edited": true` — see section 5 for drift.

## 5. Handling schema drift

When `manually_edited: true` AND `research.spec.md` changes, the next
cycle halts with `StaleManualSchemaError` and points at
`facts-schema.drift.md`. Resolution paths unchanged — merge sidecar,
remove `manually_edited`, or `--force-stale-schema`.

## 6. Validators (optional)

`<vault>/code.validators.yaml` and `code.validators.py` — unchanged.
Validators run in-process; exceptions isolate the source per D9.

## 7. Inspect failures

See **Module-Subsystem Issues** in
`<vault>/_pipeline/cycles/cycle-NNN/run-report.md`.

## 8. Per-call agent logs

`<vault>/_pipeline/cycles/cycle-NNN/agent-calls/` — full prompt/response
audit per FR-024.

## 9. Adding a new source

1. Add the instance to the right `<vault>/modules/<name>/sources.yaml`.
2. Optionally mirror it in `research.spec.md::data_sources` for scout.
3. Next cycle extracts if version changed; otherwise cache hit.

Re-extraction also happens on `bridge_version` bump or facts-schema change.

### Porting from legacy `scripts/sources.yaml`

If your vault still has a flat `<vault>/scripts/sources.yaml` from
pre-020 feeds-vault, run the one-time port when the first 020 module lands
(youtube on revival sprint). That script splits rows into per-module
`sources.yaml` files; the legacy file is not read at runtime afterward.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Module never extracts | Empty/missing `sources.yaml` | Add instances under the module folder |
| Cycle halts with `StaleManualSchemaError` | Manual schema + spec drift | Section 5 |
| Source not in signals but in `data_sources` only | Extraction uses `sources.yaml` | Add row to module `sources.yaml` |
| `sources.yaml` wiped after update | Should not happen (FR-025) | File bug — restore from git |
| Wrong module handles a URL | Trigger order | `--debug-triggers`; reorder `modules:` |
