# Quickstart: hardened `./vault update` (spec 027)

Operator-facing walkthrough of the upgrade flow once 027 ships. Reconciles with the
already-shipped Principle-X auto-commit (0.7.0) and `install.sh` hardening (0.8.0) —
you do **not** need to know those internals; this is what you'll see.

## Happy path — upgrade a vault

```bash
cd ~/Documents/<vault>
./vault update
```

You'll see, in order:

```
[update] Resolving target version …
[update] Upgrading v0.3.0 → v0.3.1
[vault-commit] committed a1b2c3d4   # ← snapshot before update 0.3.0 -> 0.3.1
[update] Upgrading framework from github.com/…@main …
[install] research_framework 0.3.1 OK
[update] Running ./vault health …
[health] PASS
[vault-commit] committed e5f6a7b8   # ← framework: upgrade to 0.3.1
```

The vault now has **two new commits**: the labelled pre-snapshot, then the upgrade.

## Already current — nothing happens

```bash
./vault update
# → Already at v0.3.1, nothing to do
```

Exits 0 in under 5 seconds. No `pip install`, no `install.sh` re-run. (SC-002)

## Dirty tree — refused

```bash
./vault update
# → Working tree is dirty. Commit or stash changes, or re-run with --force.
```

Exits non-zero in under 2 seconds. Commit your work first, or:

```bash
./vault update --force          # snapshot will include your uncommitted edits
```

(`--auto-confirm` is a *separate* flag — it suppresses install.sh's interactive
prompts, e.g. the stale-venv rebuild, for unattended runs. It does **not** override
the dirty-tree guard; only `--force` does.)

## Roll back a bad upgrade

The pre-snapshot makes rollback deterministic. Two-step (reverts both the vault tree
**and** the installed interpreter):

```bash
git reset --hard HEAD~1                       # back to "snapshot before update"
pip install research-framework==0.3.0         # back to the old framework version
```

To revert only the vault tree (keep the new framework installed):

```bash
git revert HEAD                               # one-revert rollback per Principle X
```

There is **no `./vault rollback` command** — the two-step above is the supported path
(spec 027 Clarification Q1).

## Pin a channel / tag

By default `./vault update` tracks `main` (the development tip). For production
vaults, pin an exact release tag via `RV_GITHUB_REF` (FR-008 — docs SHOULD
recommend tag-pin; override only, default unchanged):

```bash
./vault update                                # default: tracks main
RV_GITHUB_REF=v0.3.2 ./vault update           # pin to an exact tag (recommended)
```

## Downgrade — refused by default

```bash
RV_GITHUB_REF=v0.2.9 ./vault update
# → Refusing downgrade v0.3.1 → v0.2.9. Set RV_GITHUB_REF and confirm to proceed.
```

A downgrade only proceeds with an explicit pinned older `RV_GITHUB_REF` **and**
confirmation — interactive prompt on a TTY, or `--auto-confirm` for headless runs
(FR-012). This prevents an accidental downgrade clobbering a production vault
mid-run.

## User-owned files are preserved

Files the scaffold manifest marks `is_user_owned_after_first_write=true` (e.g.
`settings.yaml`, `.claude/commands/*`) are **never** regenerated by an update — your
edits survive verbatim. Framework-owned scaffolding (e.g. the `vault` shim, `AGENTS.md`)
is refreshed. (FR-006)

## Air-gapped / offline upgrade

No network? Use the release bundle directly:

```bash
pip install research_framework-0.3.1-py3-none-any.whl
bash ./bundle/install.sh                       # re-scaffolds against this vault
```

Both steps are equivalent to the online flow. Full commands live in
`docs/RELEASE.md` → "Updating an existing vault". (FR-007)
